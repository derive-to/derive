Before Derive goes public

The launch checklist. These are the items deliberately deferred from the private hardening pass (see ai-guardrails.html): they only make sense, or only work, once the repo (and the CLI) are public. Build what can be built now; flip the switches at launch.

Trigger: work through this when the decision to open-source is made. Distribution + discoverability are what convert a strong codebase into an adopted one; the public-only security checks are what let outsiders trust it.
D1

Distribution — make "CLI-first" true

The README says CLI-first, but @derive/cli is private and unpublished. This is the #1 adoption unblock.

  • Release automation. changesets across the workspace: versioned, changelog-driven releases instead of the static 0.1.0. (config can land while private; publishing waits)
  • Publish @derive/cli. Flip private:false, add description/keywords/files/author, so npm i -g @derive/cli works. Fix the README install path (today it shows the clone-and-run dev path).
  • Release workflow. publish-on-tag with npm provenance (--provenance), and GitHub Releases with notes.
  • HTTP API surface. An OpenAPI spec for the Hono API, served + checked in, so SDKs/clients can be generated.
  • Container attestation (optional). SBOM + cosign signature on the published Docker image.
D2

Discoverability + community

The repo is the landing page. Make the first 60 seconds sell it.

  • README. A demo gif/screenshot, a crisp "why Derive", and live badges (CI / version / coverage / license).
  • Docs. Consolidate the (already strong) scattered markdown into a small docs site or a clear docs/ index; add a "publish your first artifact" tutorial.
  • Community. ROADMAP.md, a labels strategy (good-first-issue), FUNDING.yml, and enable GitHub Discussions.
D3

Public-only security

The checks that need a public repo / GitHub Advanced Security, and the trust signals that only matter once others can see them.

  • CodeQL. GHAS CodeQL is free on public repos — add the workflow for JS/TS SAST.
  • OpenSSF Scorecard. The scorecard action + badge: it grades branch protection, pinned deps (done), code review, SAST, dependency updates (done). Most boxes are already ticked by the private hardening pass.
  • Best-Practices badge. Register for the OpenSSF Best Practices badge.
  • Branch protection. Require the CI gate + a review on main (a Scorecard check, and just good hygiene).

Everything that could be hardened while private is in ai-guardrails.html (Phase 1 P1–P4 + Phase 2 P5–P7). This file is only the public-launch remainder.
