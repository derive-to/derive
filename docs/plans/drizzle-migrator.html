Adopt a Drizzle-kit migrator for the schema

The review's "a new column touches 5–7 files" and "PG has no conformance guard" both trace to one root cause: drizzle-kit is configured but never run, and the schema is hand-maintained as raw-SQL string arrays. This plan replaces that with the idiomatic Drizzle flow. It changes how production schema is applied, so it ships only on your go.

Goal. Make the drizzle defs the single source: generate versioned migrations from them, run a migrator at boot for SQLite/Postgres, apply via wrangler for D1. Kill the hand-written SCHEMA_STATEMENTS / PG_SCHEMA_STATEMENTS and the try/catch ALTERs. Net: a column becomes a 1–2 file change with real history.

Where we are

  • drizzle.config.ts exists + drizzle-kit is a devDep, but there is no drizzle/ folder and nothing runs generate/migrate.
  • Tables are created at boot from three hand-written arrays: SCHEMA_STATEMENTS (sqlite, CREATE TABLE IF NOT EXISTS), MIGRATION_STATEMENTS (forward ALTERs, try/catch "already applied"), PG_SCHEMA_STATEMENTS (a separate Postgres DDL). D1's .sql is generated from the sqlite set.
  • No migrations log table, so you can't tell what state a DB is in. The drizzle defs are types-only + a conformance guard (sqlite always; pg as of this PR).

Constraints (why it's shaped this way)

Drizzle is per-dialect
Keep two schema files
pgTable ≠ sqliteTable by design; you can't share one schema. App already does this right (shared core Records + parity guard).
D1 can't self-introspect
Apply offline via wrangler
SQLITE_AUTH blocks the runtime migrator; generated SQL + wrangler d1 migrations apply is the documented path.
Existing self-hosts
Baseline carefully
Live SQLite/PG DBs already have the tables; the first migration must be a no-op baseline, not a re-create.

Plan

1Generate, don't hand-write low risk · no prod change

Two drizzle-kit configs (sqlite-family + pg) pointed at the existing defs. drizzle-kit generate emits versioned SQL into drizzle/{sqlite,pg}/. Commit them. The existing conformance tests stay as the safety net. No runtime change yet, so this is mergeable on its own and de-risks the rest.

2Baseline the live schema the careful bit

Generate an initial migration whose "up" matches today's tables, then mark it already-applied on existing DBs (insert the migration row without running the DDL). Fresh DBs run it normally. This is the one step that can corrupt a live DB if rushed; it gets its own PR + a dry-run against a prod snapshot.

3Run the migrator at boot (SQLite + Postgres)

Replace the CREATE TABLE IF NOT EXISTS + try/catch ALTER loop in sqlite.ts / pg.ts with drizzle's migrate() reading drizzle/<dialect>/. Adds a real __drizzle_migrations log. Behind a feature flag for one release so it can be reverted instantly.

4D1 via wrangler

Point wrangler.toml migrations_dir at drizzle/sqlite/; deploy runs wrangler d1 migrations apply. Drop the bespoke buildD1SchemaSql generator (the d1-schema test becomes "migrations apply cleanly"). D1 and the self-host SQLite now share one migration set.

5Delete the hand-written DDL

Once 3–4 are stable in prod for a release: remove SCHEMA_STATEMENTS, MIGRATION_STATEMENTS, PG_SCHEMA_STATEMENTS. The conformance guards retire with them (the migrator + generated SQL are now the source of truth). A column becomes: edit the two drizzle defs → drizzle-kit generate. Done.

Open decisions for you

  • Migrator vs push. Versioned migrations (recommended — gives history + safe prod) vs drizzle-kit push (simpler, no history, riskier on prod). Plan assumes migrations.
  • Baseline mechanism. Mark-applied via a tiny script, vs a hand-checked first migration. I'd do mark-applied with a prod-snapshot dry-run.
  • Scope now. Ship Phase 1 (generate + commit, zero prod risk) alongside the review fixes, and gate Phases 2–5 behind a separate go? That's my recommendation.
