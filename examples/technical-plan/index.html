Technical plan, revised in place

Move the three jobs that matter. Leave the nineteen that do not.

Twenty-two scheduled jobs run from cron on one application server. Three of them are customer-visible when they fail silently. This plan moves those three and deliberately leaves the rest alone.

The problem

A job that fails leaves no record anywhere a person will look.

Cron mails its output to a local mailbox nobody reads. When the server was replaced in January, four jobs did not run for two days and nobody noticed until an invoice was missing. Two jobs have also started to overlap: the index rebuild now takes longer than its own interval, so a second copy starts while the first is still writing.

What we are building

Four choices, and the reason for each.

PieceChoiceWhy this one
Schedulersystemd timersAlready on the host, logs to the journal, and reports failure as a unit state a monitor can read. Cron reports nothing.
QueuePostgres job tableThe database is already there and already backed up. A dedicated broker adds a component to monitor, upgrade and restore for roughly 400 jobs a day.
OverlapAdvisory lock per jobThe index rebuild cannot start twice. The lock lives with the data, so it survives a worker restart.
VisibilityA row per runThe question we could not answer, "did it run?", becomes a query.
Rollout

Two phases, because the load test said so.

Phase two was originally the same change as phase one. Splitting them is the single largest revision this plan has had, and the reason is recorded here rather than lost in a thread.

Phase one

The invoice export, alone.

It runs once a day, a person checks its output the next morning, and a missed run is recoverable by hand. It is the safest way to find out what we got wrong.

Phase two

The renewal sweep and the index rebuild.

Held until the export completes fourteen consecutive runs unassisted. The load test showed the rebuild holding a lock for around nine minutes on production shaped data, which would have blocked the sweep behind it.

Reversal conditions

What would overturn this plan.

Stated as conditions rather than dates, so they survive a schedule slipping. A recommendation that cannot be wrong is not useful.

Move to a dedicated broker if any of these become true.

  • Daily job volume passes roughly 50,000, or jobs need to fan out across workers.
  • The database becomes the bottleneck under normal load. The job table is the first thing to move off it.
  • A second application server appears. The advisory lock still holds, but the timers must run on exactly one host, which this plan does not solve.
